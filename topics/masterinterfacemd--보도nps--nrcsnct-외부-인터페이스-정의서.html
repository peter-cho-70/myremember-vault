MasterInterface.md — 보도NPS ↔︎ NRCS(NCT) 외부 인터페이스 정의서

원본: [보도NPS_NCT_A50_001]_외부인터페이스 설계서_Ver.0.95.pptx (전체 30슬라이드) 목적: AI 지원 개발(“바이브 코딩”) 시 매 세션 다시 pptx를 열어보지 않고도 바로 참조할 수 있도록, 인터페이스 스펙을 코드 관점(엔드포인트·요청/응답 필드·상태값)으로 재구성한 문서.

1. 개요

  • 연동 시스템: 보도NPS(NewsManager — MAXNINE 계열) ↔︎ NRCS(NCT — gemiso 계열)

  • 프로토콜: MOS(Media Object Server) — 방송 뉴스룸 시스템 간 표준 XML 연동 프로토콜

  • 공통 최상위 XML 구조:

    <mos>
  <mosID>news.maxnine.NewsManager</mosID>
  <ncsID>ncs.news.gemiso.com</ncsID>
  <messageID>333</messageID>
  <!-- 인터페이스별 본문 -->
</mos>

  • 전송 방식은 “누가 서버 역할인가”에 따라 달라짐 — 구현 시 가장 먼저 확인할 것: | 서버 역할 | 전송 방식 | 비고 | |—|—|—| | NRCS가 서버 | RESTful — PUT/GET + XML body | Base URL http://10.153.151.71:9200/nrcs/MosService/ | | NewsManager(NPS)가 서버 | SOAP/WSDL — 단일 함수 MosServiceCall(string aXML): string | WSDL http://ip:port/mxService?wsdl, 실배포 http://NewsNPSURL/MosServiceCall |

    SOAP 쪽은 URL 경로로 액션을 구분하지 않고, XML 내부 루트 태그(<roElementAction operation="INSERT"> 등)로 액션을 구분한다는 점이 REST 쪽과 다름.

2. 공통 규칙

2.1 공통 필드 (모든 메시지 최상위)

태그 타입 설명
mosID string 보내는 장비 ID
ncsID string NRCS ID
messageID string 메시지 고유 ID

messageID 생성 규칙: {MachineType}{MMddHHmmssffff} (월일시분초+밀리초 4자리) 예) M08091352338889

MachineType 코드 의미
N 보도정보
M 큐시트관리
T 큐시트 진행
V 송출서버운용
C 자막운용
P 프롬프트 운용

⚠️ 구현 필수 규칙: 요청/응답 메시지의 messageID는 반드시 일치해야 한다. 수신한 메시지를 다른 시스템으로 릴레이할 때는 초기 messageID를 그대로 유지한다(재생성 금지 — 이력 추적용).

3. 데이터 모델 계층

RO (큐시트/Rundown)
 └─ Story (꼭지)
     └─ Item (아이템: 영상 / 자막 / 앵커멘트)

3.1 RO(큐시트) 필드

필드 타입 설명 비고
roID string 큐시트 ID
roSlug string 프로그램명(뉴스명)
roChannel string 채널명 예: MBC (roReqAll 응답에만 존재)
roEdStart string 방송시작시간 인터페이스마다 포맷이 다름 — 아래 §7-3 참고
roEdDur string 방송길이(편성) HH:MM:SS
mosPayload.state string 방송상태 대기(확정전) / 준비(확정) / 방송중 / 완료
mosPayload.confirm string 확정유무 Y / N
mosPayload.pgmID string 프로그램 코드
mosPayload.anc string 앵커 "홍길동/갑순이" — 복수 앵커는 /로 구분
mosPayload.pd string 담당 PD "총괄PD/진행PD"
mosPayload.cgColor string 자막 지정색 특수 포맷, §7-5 참고
story list 꼭지 목록 §3.2

3.2 Story(꼭지) 필드

필드 타입 설명 비고
storyID string 꼭지 고유 ID
storySlug string 꼭지 제목
storyNum integer 순번
mosPayload.state string 방송상태 대기/준비/방송중/완료
mosPayload.orderId string 아이템 순서
mosPayload.articleID string 기사 ID
mosPayload.beginTime string 시작시간 HH:mm:ss
mosPayload.runTime int 방송길이(초) 앵커멘트+기사 합산
mosPayload.form string 형식 코드 "출", "완" 등 약물 스타일 코드
mosPayload.journalist string 기자명
mosPayload.script.num string 기사 순번
mosPayload.script.ancMent string 원본 앵커멘트
mosPayload.script.context string 원본 기사 본문
mosPayload.scriptLastDate string 기사 최종 작성시간 YYYY-MM-DD HH:mm:ss
mosPayload.sign_A string 약물 코드 A
mosPayload.sign_C string 약물 코드 C CODE를 파일명으로 사용, 송출/NRCS 양측에 동일 등록 필요
mosPayload.dveYN string 어깨걸이 여부 전체걸이 여부
mosPayload.memo string 메모
item list 아이템 목록 §3.3

3.3 Item(아이템) — 타입별 구조

아이템 종류는 mosID(장비명)와 itemID 접두 규칙으로 구분한다.

(a) 영상 아이템 — mosID: Video 계열, itemID 접두 V:

필드 타입 설명 비고
itemID string 아이템 고유ID V:0000
itemSlug string 영상 제목
objID string 매칭 시간(버전ID) = verTime
mosID string 장비명 Video
objPaths.objPath string 파일명 사용하지 않음 (deprecated)
itemEdDur string 재생길이 HH:MM:SS:FF(프레임 포함)
mosPayload.mediaInfo.contentId string 콘텐츠 ID MAM 유일 ID
mosPayload.mediaInfo.verTime int 매칭 시간 예: 110203000(시분초밀리초)
mosPayload.mediaInfo.title string 제목
mosPayload.mediaInfo.duration string 재생길이 HH:MM:SS:FF
mosPayload.mediaInfo.creator string 편집자명

(b) 자막 아이템 — mosID: CG, itemID 접두 C:

필드 타입 설명 비고
itemID string 아이템 고유ID C:0000
itemSlug string 비고
objID string Script Num 자막 위치 참조용 기사본문 번호
mosID string 장비명 CG
mosPayload.cgFile string 파일명 템플릿 파일 전체 경로+확장자
mosPayload.cgType string 자막 타입
mosPayload.cgVar string 자막 내용
mosPayload.lineNum integer 자막 위치 기사 본문 상 위치

(c) 앵커멘트 아이템 — mosID: Prompter, itemID 접두 M:

필드 타입 설명 비고
itemID string 아이템 고유ID M:1
itemSlug string 앵커멘트 제목 보통 Null
objID string 수정시간 YYYYMMDD HHmmss
mosID string 장비명 Prompter
itemEdDur string 예상 길이 HH:MM:SS:FF
mosPayload.ancMent string 앵커멘트 내용

4. 인터페이스 — NRCS가 서버 (RESTful, 큐시트)

Base URL: http://10.153.151.71:9200/nrcs/MosService/ (환경별 IP 변경 필요 — §7-8)

# 인터페이스 Method Endpoint 요청 핵심 필드 응답 핵심 필드 설명
1 Heartbeat PUT /Heartbeat time time(echo) 생존 확인
2 roReqAll PUT /RoReqAll roEdStart(방송일, YYYY-MM-DD) roListAll > ro[] (§3.1) 특정 날짜 큐시트 목록 조회
3 roReq PUT /RoReq roID roList(§3.1) + story[](§3.2) + item[](§3.3) 큐시트 상세(전체 트리) 조회
4 roListDone PUT /RoListDone ro 전체 구조(§3.1~3.3) roAck{roID, roStatus} 방송완료 큐시트 정보 저장
5 roElementAction(MOVE) PUT /RoElementAction/MOVE roID, element_target.storyID, element_source.storyID[] roAck{roID, roStatus} 꼭지 순서 이동. element_target 없으면 맨 아래로 이동
6 roElementStat(RO) PUT /roElementStat/RO roID, status, time roAck{roID, roStatus} 큐시트 전체 방송상태 갱신 — status: "01"대기/"02"준비/"03"방송중/"04"완료
7 roElementStat(STORY) PUT /RoElementStat/STORY roID, storyID, status, time roAck{roID, roStatus} 개별 꼭지 방송상태 갱신

5. 인터페이스 — NewsManager(NPS)가 서버 (SOAP, 큐시트)

WSDL: http://ip:port/mxService?wsdl / 실배포: http://NewsNPSURL/MosServiceCall 함수 시그니처: MosServiceCall(string aXML): string

# 인터페이스 XML 루트 태그 요청 핵심 필드 응답 핵심 필드 설명
1 Heartbeat <heartbeat> time time(echo) 생존 확인
2 roElementAction(INSERT) <roElementAction operation="INSERT"> roID, element_source.story(§3.2) roAck{roID, roStatus} 속보(SB) 등 신규 꼭지 삽입
3 roElementAction(REPLACE) <roElementAction operation="REPLACE"> roID, actionType("STORY"/"PITEM"/"VITEM"/"CITEM"), element_source.story roAck{roID, roStatus} 아이템/꼭지 정보 변경 — actionType으로 STORY 전체 / P(앵커멘트) / V(영상) / C(자막) 단위 구분
4 roElementStat(RO) <roElementStat element="RO"> roID, status, time roAck{roID, roStatus} 큐시트 상태 변경 수신

6. 인터페이스 — 하단롤(크롤/티커) 연동

6.1 NRCS가 서버 (RESTful, 조회 전용)

Base URL: http://10.153.151.71:9200/nrcs/MosService/

# 인터페이스 Method Endpoint 요청 응답 설명
1 mosReqObjList GET /mosReqObjList searchField.roll_id, searchField.brdc_dt(방송일) mosList > mosObj[]{objID, objSlug, objType, changed, description} 하단롤 목록 조회. 확정된 것만 조회됨
2 mosReqObj GET /mosReqObj objID mosObj{objID, objSlug, objType, changed, description} + mosExternalMetadata.mosPayload.roll_item[]{cate_nm, ctt} 하단롤 상세 조회

objType 값: TICKER, 그리고 문서상 CRAWAL로 표기(§7-6 오탈자 의심 참고)

6.2 NewsManager(NPS)가 서버 (SOAP, 생성/전송)

http://NewsNPSURL/MosServiceCall, 함수 MosServiceCall(string aXML): string

# 인터페이스 XML 루트 태그 요청 응답 설명
1 mosObjCreate <mosObjCreate> objID(Roll_ID 또는 전송일시), objSlug, objType("CRAWL"/"TICKER"/"CG"), mosExternalMetadata.mosPayload.cgFile/cgVar(CG인 경우만) mosAck{objID, status}(성공시 status Null) 속보 자막 및 하단롤 전송

7. 구현 시 주의할 점 (원본 문서에서 확인된 특이/모호 사항)

  1. 방향에 따라 프로토콜이 다르다. NRCS가 서버면 REST, NewsManager가 서버면 SOAP. 한 시스템 안에서도 “받는 인터페이스”와 “보내는 인터페이스”의 통신 방식이 다르므로, 클라이언트 구현과 서버 구현을 명확히 분리해서 설계할 것.
  2. messageID 규칙을 꼭 지킬 것 — 요청/응답 쌍 일치, 릴레이 시 재생성 금지.
  3. 방송상태 표기 방식이 인터페이스마다 다르다. RO/Story의 mosPayload.state는 문자열(대기/준비/방송중/완료)이지만, roElementStat에서는 숫자 코드("01"/"02"/"03"/"04")를 쓴다. 구현 시 이 둘을 매핑하는 테이블이 필요하다.
  4. objPaths.objPath 필드는 원본에 “사용하지 않음”으로 명시되어 있다 — 파싱은 하되 로직에서 무시해도 됨.
  5. 날짜/시간 포맷이 인터페이스마다 다르다. roEdStart가 roReqAll 요청에서는 날짜만(YYYY-MM-DD), roReq/roListDone 응답에서는 전체 일시(YYYY-MM-DDTHH:mm:ss)로 쓰인다. 파서를 인터페이스별로 분리하거나, 유연한 날짜 파서를 쓸 것.
  6. 오탈자 의심 필드: 하단롤 objType 값이 조회(§6.1)에서는 "CRAWAL", 생성(§6.2)에서는 "CRAWL"로 서로 다르게 표기됨 — 실제 연동 상대 시스템이 어느 쪽 문자열을 쓰는지 반드시 실측 확인 후 구현할 것(하드코딩 시 오탐 위험).
  7. cgColor 값 포맷이 특수하다 — 괄호 종류로 R,G,B를 구분: {,}=R,G,B / <,>=R,G,B / [,]=R,G,B. 별도 파싱 로직 필요.
  8. Base URL의 IP(10.153.151.71:9200)는 특정 환경(개발/스테이징 추정)에 하드코딩된 값이다. 실제 구현 시 환경변수/설정파일로 분리할 것. NewsNPSURL도 마찬가지로 실제 값을 확인해야 하는 플레이스홀더.
  9. 원본 pptx의 슬라이드 2(개정이력)·3(인터페이스 목록 요약표)가 Ver.0.95임에도 빈 템플릿 상태로 남아있다 — 문서 자체가 완전히 최신화되지 않았을 가능성이 있으므로, 실제 구현 착수 전 발주처/상대 시스템 담당자에게 최신 버전 여부를 확인하는 것을 권장한다.
