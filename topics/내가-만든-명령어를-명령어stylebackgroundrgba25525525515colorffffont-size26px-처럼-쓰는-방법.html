내가 만든 명령어를 /명령어 처럼 쓰는 방법

매번 똑같은 긴 지시문을 타이핑하고 계신가요? 그 지시문을 파일 하나로 저장해두면 / 슬래시 명령어가 됩니다. 만드는 데 3분, 쓰는 건 평생입니다.

3분이면 첫 명령어 완성 인자 전달 지원 복사해 쓰는 실전 예제 7종

목차

  2. 3분 만에 첫 명령어 만들기

  4. SKILL.md 파일 해부
  5. 인자 전달하기
  6. 실행 결과를 미리 넣기 (동적 주입)

  11. 데스크톱 앱(Cowork)에서 쓰려면
  12. 잘 만드는 요령 & 체크리스트

0핵심 개념: 명령어 = 스킬

예전에는 "커스텀 명령어(custom command)"와 "스킬(skill)"이 따로였지만, 지금은 하나로 합쳐졌습니다.

폴더 하나 + SKILL.md 파일 하나 = 명령어 하나. 이게 전부입니다.

~/.claude/skills/오늘정리/SKILL.md   →   /오늘정리 라고 입력하면 실행

폴더 이름이 곧 명령어 이름이 됩니다. 파일 안에는 "Claude가 이 명령을 받으면 무엇을 해야 하는지"를 평범한 한국어 문장으로 적으면 됩니다. 프로그래밍이 아닙니다.

기존에 .claude/commands/deploy.md 같은 파일을 쓰고 있었다면 그대로 계속 동작합니다. 다만 스킬 방식이 부가 파일 첨부, 인자 전달, 자동 호출 제어 같은 기능을 추가로 지원하므로 권장됩니다.

두 가지 호출 방식

방식 설명
내가 직접 호출 /명령어이름을 입력창에 타이핑
Claude가 알아서 호출 description에 적어둔 상황이 오면 Claude가 스스로 불러옴. 예: "오늘 뭐 바뀌었어?"라고 물으면 변경사항 요약 스킬이 자동 발동

둘 다 기본으로 켜져 있고, 원하면 한쪽만 켤 수도 있습니다(7장 참고).

13분 만에 첫 명령어 만들기

가장 쉬운 방법 두 가지가 있습니다. 급하면 A, 제대로 만들고 싶으면 B.

방법 A — Claude에게 시키기 (가장 쉬움)

입력창에 그냥 이렇게 말하세요.

/skill-creator

회의록을 정리하는 명령어를 만들어줘. 회의록 텍스트를 주면
① 결정사항 ② 액션 아이템(담당자 포함) ③ 다음 회의 안건
이 세 가지로 정리해주는 명령어야.

Claude가 용도를 몇 가지 되물어보고, 초안을 작성하고, 테스트 프롬프트까지 만들어 실제로 돌려본 뒤 다듬어줍니다. 처음이라면 이 방법을 추천합니다.

방법 B — 직접 파일 만들기

  1. 폴더를 만듭니다. 폴더 이름이 곧 명령어 이름이 됩니다.

    mkdir -p ~/.claude/skills/변경요약

  2. SKILL.md 파일을 만들고 내용을 씁니다. 위쪽 --- 사이가 설정, 그 아래가 실제 지시문입니다.

    ~/.claude/skills/변경요약/SKILL.md

    ---
description: 커밋하지 않은 변경사항을 요약하고 위험 요소를 짚어줌. 사용자가 "뭐 바뀌었어", "커밋 메시지 써줘", "diff 봐줘"라고 할 때 사용.
---

## 현재 변경사항

!`git diff HEAD`

## 할 일

위 변경사항을 2~3개의 불릿으로 요약해줘. 그다음 눈에 띄는 위험 요소를
나열해줘. 예: 누락된 에러 처리, 하드코딩된 값, 업데이트가 필요한 테스트.
변경사항이 없으면 "커밋할 변경사항이 없습니다"라고만 답해줘.

  3. 바로 써봅니다. 재시작할 필요 없습니다. Claude Code가 스킬 폴더 변경을 실시간으로 감지합니다.

    /변경요약

    또는 그냥 자연어로 "뭐 바뀌었어?"라고 물어도 description과 맞아떨어지면 Claude가 알아서 불러옵니다.

방금 무슨 일이 일어났나 !`git diff HEAD` 이 한 줄이 핵심입니다. Claude가 파일을 읽기 전에 이 명령이 실행되고, 그 출력이 자리에 대신 채워집니다. 그래서 Claude는 "git diff를 실행해라"가 아니라 실제 변경 내용이 이미 들어 있는 프롬프트를 받게 됩니다. 자세한 건 6장.

2어디에 저장하느냐가 범위를 정한다

같은 파일이라도 어느 폴더에 두느냐에 따라 "나만 쓸 수 있는 명령어"가 되기도, "팀 전체가 쓰는 명령어"가 되기도 합니다.

구분 경로 적용 범위
개인 ~/.claude/skills/<이름>/SKILL.md 내 모든 프로젝트에서 사용 가능
프로젝트 .claude/skills/<이름>/SKILL.md 이 프로젝트에서만. git에 커밋하면 팀 전체가 공유
플러그인 <플러그인>/skills/<이름>/SKILL.md 플러그인이 활성화된 곳. /플러그인명:스킬명으로 호출
조직(Enterprise) 관리 설정 경로 조직 전체 구성원

이름이 겹치면?

우선순위는 조직 > 개인 > 프로젝트 순입니다. 그리고 이 중 어느 위치든 같은 이름의 스킬을 두면 Claude 기본 제공 스킬을 덮어씁니다. 예를 들어 프로젝트에 code-review 스킬을 만들면 내장 /code-review 대신 내 것이 실행됩니다.

선택 기준

  • 내 업무 습관·글쓰기 스타일 → 개인 (~/.claude/skills/)
  • 이 프로젝트만의 배포 절차·코딩 규칙 → 프로젝트 (.claude/skills/, git 커밋)

3SKILL.md 파일 해부

파일은 딱 두 부분입니다: 위쪽 설정 블록(frontmatter)과 아래쪽 지시문(본문).

---
name: 배포
description: 애플리케이션을 프로덕션에 배포함
disable-model-invocation: true
allowed-tools: Bash(npm run *) Bash(git push *)
---

여기부터는 Claude가 읽을 지시문입니다. 평범한 마크다운으로 씁니다.

설정(frontmatter) 항목 — 자주 쓰는 것부터

항목 설명
description 가장 중요. 이 명령이 무엇을 하고 언제 써야 하는지. Claude는 이걸 보고 자동 호출 여부를 판단합니다. 핵심 용도를 맨 앞에 쓰세요
name 목록에 표시될 이름. 생략하면 폴더 이름 사용. (개인·프로젝트 스킬에서는 호출 이름을 바꾸지 않습니다 — 호출 이름은 항상 폴더명)
when_to_use 자동 호출 판단을 도와줄 추가 힌트. 트리거가 될 만한 표현이나 예시 요청을 적음
argument-hint 자동완성에 표시될 인자 힌트. 예: [이슈번호], [파일명] [형식]
arguments 이름 붙인 인자 목록. arguments: [issue, branch]로 선언하면 본문에서 $issue, $branch로 사용
disable-model-invocation true면 Claude가 자동으로 못 부름. 내가 /이름으로 부를 때만 실행. 배포·커밋·메시지 전송처럼 부작용 있는 작업에 필수
user-invocable false면 / 메뉴에 안 뜸. Claude만 참고하는 배경 지식용
allowed-tools 이 명령 실행 턴 동안 승인 없이 쓸 수 있는 도구. 예: Bash(git add *) Bash(git commit *)
disallowed-tools 반대로 이 명령이 활성일 때 아예 못 쓰게 막을 도구
model 이 명령을 실행할 때 쓸 모델 지정. 끝나면 원래 모델로 복귀
effort 이 명령 실행 시 추론 강도. low~max
context fork로 설정하면 별도 서브에이전트에서 격리 실행 (9장)
agent context: fork일 때 어떤 에이전트를 쓸지. Explore, Plan, general-purpose 등
paths 특정 파일 패턴을 다룰 때만 자동 발동하도록 제한. 예: src/**/*.tsx

전부 선택 사항이며, 실질적으로 description 하나만 잘 써도 동작합니다.

본문은 짧게 한 번 호출된 스킬 내용은 세션 내내 컨텍스트에 남습니다. 즉 모든 줄이 반복 비용입니다. "왜"와 "어떻게"를 장황하게 설명하지 말고 "무엇을 하라"만 적으세요. SKILL.md는 500줄 이내를 권장하며, 긴 참고자료는 별도 파일로 분리하세요.

부가 파일 붙이기

템플릿, 예시, 참고문서, 스크립트를 같은 폴더에 두고 본문에서 언급하면 Claude가 필요할 때만 열어봅니다.

내명령어/
├── SKILL.md          ← 필수. 개요와 지침
├── reference.md      ← 상세 참고자료 (필요할 때만 로드)
├── examples.md       ← 결과물 예시
└── scripts/
    └── helper.py     ← 실행용 스크립트

SKILL.md 안에 이렇게 적어두면 됩니다: 자세한 규칙은 [reference.md](reference.md) 참고

4인자 전달하기

/명령어 뒤에붙인말에서 뒤에 붙인 말을 명령어 안에서 받아 쓰는 방법입니다.

① 전부 통째로 받기 — $ARGUMENTS

~/.claude/skills/이슈수정/SKILL.md

---
description: GitHub 이슈를 수정함
disable-model-invocation: true
argument-hint: [이슈번호]
---

GitHub 이슈 $ARGUMENTS 를 우리 코딩 규칙에 맞게 수정해줘.

1. 이슈 내용을 읽는다
2. 요구사항을 파악한다
3. 수정을 구현한다
4. 테스트를 작성한다
5. 커밋을 만든다

/이슈수정 123 이라고 치면 $ARGUMENTS 자리에 123이 들어갑니다.

② 순서대로 나눠 받기 — $0, $1, $2

---
description: 컴포넌트를 다른 프레임워크로 이전
---

$0 컴포넌트를 $1 에서 $2 로 이전해줘.
기존 동작과 테스트는 모두 보존할 것.

/이전 SearchBar React Vue → $0=SearchBar, $1=React, $2=Vue

여러 단어를 하나의 인자로 넘기려면 따옴표로 감싸세요: /명령 "안녕 세상" 두번째

③ 이름 붙여 받기 — $이름

---
description: 이슈를 브랜치에서 수정
arguments: [issue, branch]
argument-hint: [이슈번호] [브랜치명]
---

$branch 브랜치에서 이슈 $issue 를 수정해줘.

명령어를 여러 개 이어 붙이기 한 메시지 앞부분에 스킬을 여러 개 나열할 수 있습니다. /테스트작성 /이슈수정 123 이라고 치면 두 스킬이 모두 로드되고, 뒤의 123이 양쪽 모두에 인자로 전달됩니다. 최대 6개까지 연결 가능합니다.

$ARGUMENTS를 본문에 안 써놨는데 인자를 넘기면? 내용 맨 끝에 ARGUMENTS: 입력한말 형태로 자동으로 붙습니다. 그래서 그냥 넘겨도 Claude는 알아봅니다.

5실행 결과를 미리 넣기 (동적 주입)

이 기능이 커스텀 명령어를 진짜 강력하게 만듭니다.

!`명령어` 문법을 쓰면, Claude가 파일을 보기 전에 그 셸 명령이 실행되고 출력 결과가 그 자리에 채워집니다. Claude는 "명령을 실행하라"는 지시가 아니라 이미 데이터가 들어찬 완성된 프롬프트를 받습니다.

## 현재 상황
- 브랜치: !`git branch --show-current`
- 변경 파일: !`git diff --name-only`
- 최근 커밋 5개: !`git log --oneline -5`

## 할 일
위 상황을 보고 오늘 작업 내용을 팀에 공유할 메시지를 작성해줘.

여러 줄 명령을 실행하려면 ```! 로 시작하는 코드 블록을 쓰세요.

```!
node --version
npm --version
git status --short
```

문법 주의 !는 줄 맨 앞이나 공백 바로 뒤에 있어야 인식됩니다. KEY=!`cmd`처럼 다른 글자 뒤에 붙으면 그냥 글자로 취급되어 실행되지 않습니다.

유용한 경로 변수

변수 의미
${CLAUDE_SKILL_DIR} 이 SKILL.md가 있는 폴더. 함께 넣어둔 스크립트를 부를 때 사용
${CLAUDE_PROJECT_DIR} 프로젝트 루트 경로
${CLAUDE_SESSION_ID} 현재 세션 ID. 세션별 로그 파일 만들 때 유용
${CLAUDE_EFFORT} 현재 추론 강도 (low~max)

6누가 호출할 수 있게 할까

기본값은 "나도 부를 수 있고 Claude도 알아서 부를 수 있음"입니다. 두 개의 설정으로 이걸 조절합니다.

설정 내가 호출 Claude가 호출 컨텍스트 점유
기본값 (아무것도 안 씀) 가능 가능 설명문이 항상 컨텍스트에 있음
disable-model-invocation: true 가능 불가 설명문도 컨텍스트에 없음 (부를 때만 로드)
user-invocable: false 불가 가능 설명문이 항상 컨텍스트에 있음

disable-model-invocation: true를 꼭 써야 하는 경우

되돌릴 수 없거나 외부에 영향을 주는 작업입니다.

  • /배포 — 코드가 그럴듯해 보인다고 Claude가 알아서 배포하면 곤란합니다
  • /커밋, /푸시
  • /슬랙전송, /메일발송

보너스: 컨텍스트 절약 효과 disable-model-invocation: true를 붙이면 그 스킬의 설명문조차 평소에 컨텍스트를 차지하지 않습니다. 명령어를 많이 만들어도 부담이 없어집니다.

7도구 미리 승인하기

명령을 실행할 때마다 "이 bash 명령 실행해도 될까요?" 하고 물어보는 게 번거롭다면.

allowed-tools에 적어두면 그 명령을 호출한 턴 동안만 승인 없이 실행됩니다. 다음 메시지를 보내면 권한은 자동으로 사라집니다.

~/.claude/skills/커밋/SKILL.md

---
description: 현재 변경사항을 스테이징하고 커밋
disable-model-invocation: true
allowed-tools: Bash(git add *) Bash(git commit *) Bash(git status *)
---

변경사항을 확인하고, 관련 있는 것끼리 묶어서 커밋해줘.
커밋 메시지는 한국어로, "무엇을 왜 바꿨는지"가 드러나게 써줘.

함께 넣어둔 스크립트를 물어보지 않고 실행시키려면 ${CLAUDE_SKILL_DIR}을 양쪽에 똑같이 쓰면 됩니다.

---
description: CSV로 차트 렌더링
allowed-tools: Bash(${CLAUDE_SKILL_DIR}/scripts/render.sh *)
---

`${CLAUDE_SKILL_DIR}/scripts/render.sh <csv파일>` 을 실행해서 차트를 만들어줘.

보안 주의 프로젝트 .claude/skills/에 있는 스킬의 allowed-tools는 해당 폴더를 신뢰하겠다고 승인한 뒤에 적용됩니다. 남의 저장소를 신뢰하기 전에 스킬 내용을 먼저 읽어보세요. 스킬이 스스로에게 광범위한 권한을 부여할 수 있습니다.

8서브에이전트로 격리 실행

결과물은 짧은데 과정이 방대한 명령이라면, 별도 공간에서 돌리고 요약만 받아오세요.

context: fork를 넣으면 이 명령은 독립된 컨텍스트에서 실행됩니다. 대량의 파일 읽기가 내 대화를 오염시키지 않고, 결과 요약만 돌아옵니다. 기본적으로 백그라운드에서 돌아가므로 그동안 나는 다른 작업을 계속할 수 있습니다.

~/.claude/skills/코드조사/SKILL.md

---
description: 특정 주제에 대해 코드베이스를 깊이 조사
context: fork
agent: Explore
---

$ARGUMENTS 에 대해 철저히 조사해줘:

1. Glob과 Grep으로 관련 파일을 찾는다
2. 코드를 읽고 분석한다
3. 구체적인 파일 경로와 함께 결과를 요약한다

agent에는 Explore(읽기 전용 탐색 특화), Plan, general-purpose 또는 직접 만든 서브에이전트를 지정할 수 있습니다. 생략하면 general-purpose입니다.

주의: 지시문이 없으면 무의미합니다 context: fork는 구체적인 작업 지시가 있는 명령에만 의미가 있습니다. "이런 API 규칙을 따라라" 같은 참고 지식만 담긴 스킬을 fork하면, 서브에이전트가 지침만 받고 할 일이 없어 빈손으로 돌아옵니다.

더 깊이 생각하게 하려면 스킬 본문 아무 곳에나 ultrathink라는 단어를 넣으면 그 명령 실행 시 더 깊은 추론을 요청합니다.

9복사해 쓰는 실전 예제 7종

폴더를 만들고 아래 내용을 SKILL.md로 저장하면 바로 동작합니다.

① /일일정리 — 오늘 한 일 정리해서 노트에 남기기

저장 위치: ~/.claude/skills/일일정리/SKILL.md

---
description: 오늘의 작업을 정리해 NOTES.md에 기록. 하루를 마무리하거나 작업을 인계할 때 사용.
disable-model-invocation: true
allowed-tools: Bash(git log *) Bash(git diff *)
---

## 오늘의 커밋
!`git log --oneline --since="6am"`

## 미완료 변경사항
!`git status --short`

## 할 일
위 정보와 이번 대화 내용을 종합해서 `NOTES.md` 파일 맨 아래에
오늘 날짜로 이어쓰기 해줘. 형식은:

1. 완료한 것
2. 확정된 결정과 그 이유
3. 미해결 문제와 지금까지 시도한 방법
4. 다음에 할 일 (우선순위 순)

다음 세션에서 이 파일만 읽고도 바로 이어서 작업할 수 있을 만큼
구체적으로 써줘.

② /이어서 — 지난 작업 맥락 복원하기

저장 위치: ~/.claude/skills/이어서/SKILL.md

---
description: NOTES.md와 CLAUDE.md를 읽고 지난 작업 맥락을 복원한 뒤 다음 할 일부터 시작. 새 세션을 시작할 때 사용.
disable-model-invocation: true
---

`NOTES.md`와 `CLAUDE.md`를 읽고 현재 상황을 파악해줘.

그다음 파악한 내용을 이렇게 정리해서 나에게 확인받아:
- 지금 어디까지 왔는지 (2줄)
- 다음에 할 일 (1줄)
- 내가 알아야 할 주의사항이 있다면 (있을 때만)

내가 확인해주면 그때부터 작업을 시작해줘.

③ /회의록 — 회의 내용을 구조화

저장 위치: ~/.claude/skills/회의록/SKILL.md

---
description: 회의 내용을 결정사항·액션아이템·다음안건으로 구조화. 회의 메모나 녹취를 정리할 때 사용.
argument-hint: [회의 내용 또는 파일 경로]
---

다음 회의 내용을 정리해줘: $ARGUMENTS

출력 형식:

## 결정사항
- (확정된 것만. 논의 중인 건 제외)

## 액션 아이템
| 할 일 | 담당자 | 기한 |
|---|---|---|

## 다음 회의 안건
- (결론 안 난 것들)

## 확인 필요
- (누가 담당인지 불분명하거나 정보가 부족한 항목)

담당자나 기한이 언급되지 않은 액션 아이템은 "미정"으로 표기하고
"확인 필요"에도 함께 적어줘.

④ /커밋 — 변경사항을 의미 단위로 나눠 커밋

저장 위치: .claude/skills/커밋/SKILL.md (프로젝트별)

---
description: 변경사항을 의미 단위로 묶어 커밋
disable-model-invocation: true
allowed-tools: Bash(git add *) Bash(git commit *) Bash(git status *) Bash(git diff *)
---

## 현재 상태
!`git status --short`

## 변경 내용
!`git diff HEAD`

## 할 일
관련 있는 변경끼리 묶어서 여러 개의 커밋으로 나눠줘.
커밋 메시지 규칙:
- 첫 줄: 50자 이내, 한국어, "무엇을" 중심
- 본문: 왜 이렇게 바꿨는지 (자명하면 생략)
- 이슈 번호가 있으면 마지막 줄에 참조

커밋하기 전에 어떻게 나눌 계획인지 먼저 보여주고 내 확인을 받아줘.

⑤ /문서화 — 내 스타일로 HTML 문서 만들기

저장 위치: ~/.claude/skills/문서화/SKILL.md

---
description: 조사한 내용을 정해진 스타일의 HTML 가이드 문서로 만듦. 사용자가 "HTML로 정리해줘", "문서로 만들어줘"라고 할 때 사용.
argument-hint: [주제]
---

$ARGUMENTS 에 대한 HTML 가이드 문서를 만들어줘.

## 반드시 지킬 형식
- 한국어, 단일 HTML 파일 (CSS 내장, 외부 의존성 없음)
- 상단 그라데이션 히어로 헤더 + 2단 목차
- 섹션마다 번호 원형 배지
- 표는 둥근 모서리 + 헤더 배경색
- 복사해 쓸 수 있는 예시는 코드 블록으로
- 팁/주의/금지는 각각 다른 색 박스로 구분
- 다크 계열 코드 블록

## 작업 순서
1. 먼저 웹 검색으로 최신 정보를 확인한다 (추측 금지)
2. 목차 구조를 잡는다
3. 문서를 작성해 outputs 폴더에 저장한다
4. 태그 짝이 맞는지 검증한다

자세한 스타일 규칙은 [style.md](style.md) 참고.

같은 폴더에 style.md를 만들어 색상 팔레트나 CSS 스니펫을 넣어두면 매번 일관된 결과가 나옵니다.

⑥ /조사 — 컨텍스트를 아끼는 심층 조사

저장 위치: ~/.claude/skills/조사/SKILL.md

---
description: 주제를 깊이 조사하고 요약만 반환. 파일을 많이 읽어야 하는 조사 작업에 사용.
context: fork
agent: Explore
argument-hint: [조사할 주제]
---

$ARGUMENTS 에 대해 조사해줘.

1. 관련 파일을 찾는다 (Glob, Grep)
2. 내용을 읽고 분석한다
3. 결과를 아래 형식으로 요약한다

## 요약 (3줄 이내)
## 관련 파일과 역할
| 경로 | 역할 |
## 주의할 점

파일 전문은 반환하지 말고, 인용이 꼭 필요하면 5줄 이내로만.

⑦ /컨텍스트정리 — 압축 전 점검

저장 위치: ~/.claude/skills/컨텍스트정리/SKILL.md

---
description: 현재 컨텍스트 상황을 점검하고 보존할 항목을 정리한 뒤 압축을 제안
disable-model-invocation: true
---

지금 이 대화에서 반드시 보존해야 할 항목을 정리해줘:

1. 확정된 결정과 그 이유
2. 아직 미해결인 문제와 시도해본 방법
3. 다음 단계 계획
4. 내가 명시적으로 요청한 제약 조건

정리한 목록을 보여준 다음, 그 항목들을 지시문에 넣은
`/compact` 명령문을 완성해서 제안해줘.
(내가 복사해서 바로 실행할 수 있게)

10데스크톱 앱(Cowork)에서 쓰려면

중요한 차이가 하나 있습니다.

Cowork와 클라우드 세션은 내 컴퓨터의 ~/.claude/skills/를 읽지 않습니다 데스크톱 앱의 Cowork 세션과 클라우드 세션(정기 실행 루틴 포함)은 claude.ai 계정에 등록된 스킬을 세션 시작 시 동기화해서 씁니다. 터미널의 Claude Code와는 별개입니다.

Cowork에서 쓸 수 있게 하는 방법

  1. 스킬 폴더를 ZIP으로 압축합니다. 폴더가 ZIP의 최상위 루트여야 합니다 (파일들이 루트에 흩어지면 안 됨).
  2. 데스크톱 앱 사이드바의 Customize → Skills (또는 claude.ai의 스킬 설정)으로 이동합니다.
  3. "+" → "Create skill" → "Upload a skill"로 ZIP을 올립니다.
  4. 목록에서 토글을 켜면 Cowork 세션에서 사용 가능해집니다.

Mac 사용자라면 화면 녹화로 스킬을 만드는 방법도 있습니다. 작성창의 "+" → "Record a skill"로 평소 하던 작업을 녹화하면 Claude가 스킬 초안을 제안해줍니다.

업로드 시 주의: 사용 가능한 설정 항목이 제한됩니다 claude.ai에 업로드하는 스킬은 name, description, license, compatibility, metadata, allowed-tools 이 여섯 개 항목만 허용됩니다. argument-hint나 context: fork 같은 Claude Code 전용 항목이 들어 있으면 업로드가 실패합니다.

또한 !`명령어` 동적 주입 같은 Claude Code 전용 본문 기능도 claude.ai 채팅에서는 작동하지 않습니다.

정리하면

  • 터미널 Claude Code에서만 쓸 명령어 → 모든 기능 사용 가능, ~/.claude/skills/에 저장
  • Cowork·모바일·웹에서도 쓸 명령어 → 여섯 개 항목만 쓰고 ZIP으로 업로드

11잘 만드는 요령 & 체크리스트

description이 8할이다

Claude가 자동 호출할지 말지를 오직 이 문장 하나로 판단합니다. 두 예시를 비교해보세요.

나쁜 예 description: 문서 관련 작업 — 언제 써야 하는지 알 수 없습니다.

좋은 예 description: 조사 결과를 정해진 스타일의 HTML 가이드로 만듦. 사용자가 "HTML로 정리해줘", "문서로 만들어줘", "가이드 만들어줘"라고 할 때 사용. — 실제 트리거가 될 표현이 들어 있습니다.

핵심 용도를 맨 앞에 쓰세요. description과 when_to_use를 합친 텍스트는 1,536자에서 잘립니다.

만들 때 체크리스트

  • 폴더 이름이 내가 타이핑하고 싶은 명령어 이름과 같은가
  • description에 "언제 쓰는지"와 실제 트리거 표현이 들어 있는가
  • 부작용이 있는 명령이라면 disable-model-invocation: true를 넣었는가
  • 본문이 500줄 이내인가 (긴 참고자료는 별도 파일로)
  • "왜"가 아니라 "무엇을 하라"로 썼는가
  • 출력 형식을 구체적으로 지정했는가 (표, 불릿, 순서 등)
  • 매번 반복되는 셸 명령이 있다면 !`명령`으로 미리 주입했는가
  • 실제로 두세 번 다른 표현으로 불러보며 테스트했는가

자주 겪는 문제

증상 확인할 것
Claude가 명령어를 안 부름 description이 모호하지 않은지, disable-model-invocation이 켜져 있진 않은지. 명시적으로 /이름으로 불러보기
명령어 목록에 안 뜸 폴더 위치가 맞는지(~/.claude/skills/이름/SKILL.md), user-invocable: false가 아닌지. /reload-skills로 재스캔
첫 응답 후 효과가 사라짐 내용은 남아 있지만 모델이 다른 방식을 택한 것. description과 지시문을 더 단호하게 쓰거나, 압축 후라면 다시 호출
!`명령`이 실행 안 됨 !가 줄 맨 앞이나 공백 뒤에 있는지 확인
Cowork에서 안 보임 claude.ai 계정에 업로드했는지 확인. 로컬 ~/.claude/skills/는 Cowork에서 안 읽힙니다
업로드 실패 허용되지 않는 frontmatter 항목이 있는지, ZIP 구조가 맞는지 확인

가장 좋은 시작점 완벽하게 설계하려 하지 말고, 지난 일주일간 두 번 이상 타이핑한 긴 지시문을 하나 골라서 그대로 SKILL.md에 붙여넣는 것부터 시작하세요. 쓰면서 다듬으면 됩니다.
